ぶちこむ家計簿の仕組み

LINE に「500 ランチ」と送るだけで記録できる、ふたり暮らし向け家計簿の全体構成。どこで何が動き、データがどう流れ、どう守られ、どうデプロイされるかを 1 枚にまとめた。詳細はリポジトリの docs/ にある。

Web: Next.js 16 on Vercel Bot: Firebase Functions gen2 / Node 22 Data: Firestore + Cloud Storage AI: Gemini 3.5 Flash-Lite 世帯: 2 名固定

全体像

入口は LINE・Gmail・スケジュール・Web の 4 つ。書き込みは原則すべて bot を通る。

Web はブラウザから Firestore を直接読む（セキュリティルールで世帯メンバーに限定）。確認・精算・固定費の登録のように状態を変える操作は、ID トークン付きで bot の api 関数に送る。

主なデータの流れ

支出はどの入口から入っても expenses コレクションの 1 件になる。

LINE のテキスト入力

  1. 「6/29 4800 家賃」を受信、署名を検証
  2. 金額・日付・支払方法・内容を解析
  3. カテゴリを分類（下の 3 段）
  4. 支出を保存し確認カードで返信
  5. カードの OK / 修正 / 立替 / 除外で更新
bot/src/index.ts · line/

カード利用メール

  1. Gmail の新着を Pub/Sub で受信
  2. 本文から金額・店名・利用日時を抽出
  3. 日付+金額 → 店名の類似 → 時刻 ±1 分で重複を除外
  4. 保存して LINE グループに通知
bot/src/gmail/

固定費

  1. Web の設定で家賃・光熱費などを見込み額と引き落とし日で登録
  2. 毎朝、当日が引き落とし日の項目を計上
  3. ID は recurring_{項目}_{年月} で重複しない
  4. 実額が分かったら Web で修正
bot/src/recurringExpenses.ts

立替の精算

  1. 立替は「未精算」として残る
  2. 未精算の立替から精算額を計算（GET /household/settlement）
  3. 「精算を記録」で立替が精算済みになる
  4. 精算済みは金額・日付・支払者の変更と削除ができない（内容・カテゴリは直せる）
bot/src/householdSettlement.ts

期間の折半

  1. 精算タブで期間の支出合計を 2 で割る
  2. 送金する人の支払いとの差から「誰が誰にいくら送金するか」を表示
  3. 表示だけで、何も記録しない（送金する人の設定だけ保存）
web/lib/periodSplit.ts

カテゴリ分類

LINE の入力は費用のかからない方法から試す。カードの店名は取り違えやすいので Gemini を先に使う。19 カテゴリ。

1. キャッシュ関数のメモリ上に残っている同じ内容の分類結果を再利用費用 0
2. キーワード辞書「ランチ」→ 食費 など全カテゴリの辞書費用 0
3. Geminiそれでも決まらないものだけ問い合わせ（3.5 Flash-Lite、思考は最小、カテゴリ一覧の中から選ばせる。使うのは Flash-Lite だけ。一番新しい Flash-Lite を自動で選び、終了したら次の Flash-Lite に切り替え）API 呼び出し

上は LINE の入力（「500 ランチ」の「ランチ」）の順序。カード利用メールの店名（「ｾﾌﾞﾝ-ｲﾚﾌﾞﾝ」「AMAZON.CO.JP」など）は、辞書の部分一致だと「au」「etc」「パン」などが店名の一部に当たって取り違えるため、キャッシュ → Gemini → 辞書の順にしている。Gemini が使えないときは辞書だけで動き、分類できなければ「その他」になる。

認証とアクセス制御

URL に載った ID は信用しない。本人確認はすべてトークンで行う。

  • ログイン: LIFF の ID トークンを /auth/line が LINE に照会し、lineId クレーム付きの Firebase カスタムトークンを発行する。
  • Firestore ルール: 世帯のデータは groupMembers/{groupId}_{lineId} が有効なメンバーだけが読める。支出の項目は型と値を検証し、精算済みの立替は金額・日付・支払者の変更と削除を拒否する。
  • Storage ルール: レシート画像は Firestore のメンバー情報を参照して制限（cross-service rules）。
  • /household API: ID トークンを検証し、世帯メンバーかを確認。レート制限と CORS の許可リストあり。
  • 世帯は 2 名固定: メンバーの追加・無効化は bot ではなく管理スクリプト scripts/manage-group-members.mjs で行う。
  • シークレット: LINE のトークンなどは Secret Manager に置き、関数は宣言した名前だけを読む。

デプロイとリリース

master にマージすれば全部自動。master への直接コミットはしない。

対象いつどうやって
Webmaster へのマージ（PR はプレビュー）Vercel の Git 連携
Bot・ルールmaster へのマージで bot / ルールに変更があるときci-cd.yml の deploy-bot → post-deploy-check
タグ・Release実装のマージごとrelease.yml が vX.Y.Z と GitHub Release を作成

バージョンの上げ方（PR タイトルで決まる）

feat: → minor fix: / refactor: / perf: → patch feat!: / BREAKING CHANGE: → major docs: / chore: / ci: → タグなし

PR ごとに CI が型チェック・lint・ビルド・テスト・CodeQL・ルールのテストを行い、通ったものだけを squash マージする。バージョンは git タグが正で、package.json の version は使わない。

リポジトリの docs/ARCHITECTURE.md・SPECIFICATION.md・SETUP.md・SECURITY_OPERATIONS.md を元に作成。
